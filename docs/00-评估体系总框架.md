# 知识库模型评估：Embedding 与 Reranker 全量测评体系

> **文档版本**：v1.0  
> **调研基准日期**：2026-10-21  
> **用途**：为企业知识库 / RAG 平台在内网选择、部署、验证 Embedding 与 Reranker 模型提供统一的测评标准、指标口径、测试用例设计、部署建议与报告规范。  
> **选型重点**：Qwen3-Embedding-8B、Qwen3-Reranker-8B 作为高精度候选，同时比较 Qwen3 小参数量模型与 BGE 系列模型。  
> **重要声明**：本文将“官方公开 benchmark 结果”“项目建议验收线”“本地实测结果”分开记录。公开榜单分数受版本、数据集、检索候选集、提示词、截断长度、硬件和实现影响，不允许把条件不同的分数直接当作严格的横向结论。

---

## 1. 项目目标与交付物

本项目不以“哪个模型参数最大”或“某一张榜单第一”为唯一结论，而是判断模型在企业知识库生产环境下的**检索质量、重排收益、性能、资源成本、稳定性与可维护性**。

### 1.1 最终需要回答的问题

1. 哪个 Embedding 在中文半导体专业问题、英文资料、缩写/料号/报警代码、长文档、跨语言问题上的召回质量最好？
2. 哪个 Reranker 能最大幅度提升初召回结果，尤其是 Top-5 / Top-10 的排序质量？
3. Qwen3-Embedding-8B / Qwen3-Reranker-8B 相对 0.6B、4B 和 BGE 的质量提升，是否值得额外 GPU 显存、延迟和部署成本？
4. 检索效果是否依赖特定指令、向量维度、最大输入长度、归一化、分块策略或候选集？
5. 在相同硬件、相同语料、相同候选集、相同指标定义下，能否重跑得到一致结论？
6. 模型对知识库平台的端到端 RAG 质量究竟带来多少收益？

### 1.2 交付物

- 固定版本的公开 benchmark 复现记录。
- 半导体领域内部标准测试集及其标注指南。
- Embedding、Reranker、组合链路的自动化评测脚本。
- 模型和推理参数登记表、硬件与吞吐测试记录。
- 可追溯的 JSON/CSV 原始结果、汇总报表、模型排名与推荐结论。
- 离线部署说明、模型文件校验记录、依赖版本锁定文件。

## 2. 测评范围：要测什么

### 2.1 三个独立层次，不要混为一谈

| 层次 | 被测对象 | 核心问题 | 主要指标 |
|---|---|---|---|
| L1：模型能力 | Embedding 向量编码器 | 正确相关文档是否能进入候选集？ | Recall@K、Hit@K、nDCG@K、MRR@K |
| L2：重排能力 | Reranker | 给定同一候选集时，能否把正确答案排到前面？ | nDCG@K、MRR@K、MAP、Precision@K、Pairwise Accuracy |
| L3：系统能力 | Embedder + 向量检索 / 混合检索 + Reranker | 实际知识库链路是否更准、更快、更稳定？ | 端到端检索质量、P50/P95 延迟、QPS、显存、成本、失败率 |

**原则**：评测 Reranker 时必须固定候选集。若每个 Reranker 用不同 Embedder 产生候选集，测出的分数就混合了“召回差异”和“重排差异”。评估最终系统时再测完整链路。

### 2.2 必须覆盖的能力维度

| 维度 | 要覆盖的测试内容 | 典型失败模式 |
|---|---|---|
| 中文语义检索 | 同义改写、口语问法、上下位概念 | 只匹配字面词，漏掉语义等价段落 |
| 英文与中英混合 | 英文手册、中文提问、缩写和中英混写 | 跨语言召回弱、术语被错误切分 |
| 精确术语与标识符 | 设备型号、工艺步骤、报警码、配方名、料号 | 语义相似但关键编号不一致 |
| 数值与约束 | 温度、压力、时间、尺寸、阈值、单位 | 找到类似参数却忽略数值或单位差异 |
| 长文档 | 长手册、工艺规范、多个章节、跨页资料 | 长输入截断、关键内容在尾部时召回下降 |
| 多粒度文档 | 标题、段落、表格、FAQ、步骤、章节 | 表格行脱离表头后失去语义 |
| 难负例区分 | 近似设备、相邻工艺、旧版本文件 | 把高度相似但不适用的内容排在前面 |
| 多语言与跨语言 | 中文问英文资料、英文问中文资料 | 只能同语言检索，跨语言效果显著下降 |
| 指令敏感性 | 有/无 instruction、不同任务指令 | 参数默认值变化导致结果难复现 |
| 向量工程参数 | 维度、归一化、距离函数、批量大小 | 索引与查询向量设置不一致 |
| 重排鲁棒性 | 不同候选集质量、候选数量、极端长文本 | 候选数量增加后延迟激增或排序不稳 |
| 在线性能 | 单请求、并发、持续压力、冷启动 | P95 延迟长、吞吐量下降、显存溢出 |
| 工程可运维性 | 离线启动、异常恢复、版本锁定、日志 | 依赖冲突、模型缓存不完整、难以追责 |
| 安全边界（系统层） | 权限过滤后的召回、跨知识库隔离 | 检索召回越权文档（属于系统安全测试，不归因于模型本身） |

## 3. 候选模型池与基础参数

首先比较同类模型，再比较最终链路。下表是候选池建议；具体文件版本、模型 revision、量化版本必须在每次实验中登记。

### 3.1 Embedding 候选模型

| 模型 | 规模 / 关键特征 | 优势和适合场景 | 需要注意 |
|---|---|---|---|
| `Qwen/Qwen3-Embedding-8B` | 约 8B；最长 32K；最大向量维度 4096；支持 MRL 可变维度、指令 | 高精度基线；中英混合、长输入、复杂语义的重点候选 | 显存与吞吐成本较高；需确认指令模板和向量维度 |
| `Qwen/Qwen3-Embedding-4B` | 约 4B；最长 32K；最大维度 2560；支持 MRL、指令 | 精度与资源的折中候选，必须作为 8B 的核心对照 | 不能假设质量一定比 0.6B 成比例提升 |
| `Qwen/Qwen3-Embedding-0.6B` | 约 0.6B；最长 32K；最大维度 1024；支持 MRL、指令 | 高性价比、批量编码、低延迟候选；可作为检索初召回默认对照 | 仍需按领域测试；小模型不等于一定更快，取决于长度/批量/硬件 |
| `BAAI/bge-m3` | 约 0.6B；多语言；支持 dense、sparse lexical、multi-vector；文档强调最长约 8192 tokens | 适合混合检索、多语言、希望一模型提供多种召回路径的场景 | dense/sparse/ColBERT 不是同一指标；必须分别测并比较融合方案 |
| `BAAI/bge-large-zh-v1.5` | 中文稠密向量基线 | 中文知识库对照；容易建立标准化 baseline | 模型代际相对较早，需用相同测试集重新测 |
| `BAAI/bge-base-zh-v1.5` | 较小中文稠密向量基线 | 资源受限、延迟敏感场景 | 中文通用能力不能代表半导体领域表现 |
| `BAAI/bge-large-en-v1.5` / `bge-base-en-v1.5` | 英文稠密向量对照 | 英文原始文档占比高时作为对照 | 不应直接作为主要中英统一模型，除非实测支持 |

官方参考： [Qwen3-Embedding-8B 模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-8B)、[BGE-M3 官方文档](https://github.com/FlagOpen/FlagEmbedding/blob/master/docs/source/bge/bge_m3.rst)、[FlagEmbedding / BGE 项目](https://github.com/FlagOpen/FlagEmbedding)。Qwen3 模型卡记录其 0.6B / 4B / 8B 系列均支持指令感知；官方建议为查询侧编写任务指令，并指出多数检索任务可能有约 1%–5% 的变化，故指令必须作为受控实验因素，而不能临时调整。

### 3.2 Reranker 候选模型

| 模型 | 规模 / 类型 | 建议用途 | 需要注意 |
|---|---|---|---|
| `Qwen/Qwen3-Reranker-8B` | 约 8B；cross-encoder / 相关性打分；最长上下文系列规格为 32K | 高精度候选，重点看中文、长文档、专业术语和难负例 | 延迟、显存和并发成本高；官方 benchmark 条件是固定 top-100 候选，不能把它当成任意链路分数 |
| `Qwen/Qwen3-Reranker-4B` | 约 4B | 8B 的关键性价比对照 | 官方公开结果中部分英语/指令跟随指标高于 8B，因此不能默认 8B 全面优胜 |
| `Qwen/Qwen3-Reranker-0.6B` | 约 0.6B | 低成本重排和大吞吐候选 | 需要检查在半导体近似负例上的准确性 |
| `BAAI/bge-reranker-v2-m3` | 约 0.6B；多语言 cross-encoder | 强力轻量多语言对照 | 要统一 tokenizer、最大长度、候选集和推理精度 |
| `BAAI/bge-reranker-large` / `BAAI/bge-reranker-base` | cross-encoder | 对比经典 BGE 排序模型 | base/large 与 v2-m3 不是相同架构规格，按实测与硬件确定 |

官方参考：[Qwen3-Reranker-8B 模型卡](https://huggingface.co/Qwen/Qwen3-Reranker-8B)、[BGE-Reranker-v2-m3 模型卡](https://huggingface.co/BAAI/bge-reranker-v2-m3)、[FlagEmbedding 官方评测与推理实现](https://github.com/FlagOpen/FlagEmbedding)。

### 3.3 最低模型组合清单

第一轮至少完成：

1. Qwen3-Embedding-0.6B + Qwen3-Reranker-0.6B。
2. Qwen3-Embedding-4B + Qwen3-Reranker-4B。
3. Qwen3-Embedding-8B + Qwen3-Reranker-8B。
4. BGE-M3 dense-only。
5. BGE-M3 dense + sparse 融合（如系统支持）。
6. 一个中文 BGE embedding + `bge-reranker-v2-m3`。
7. BM25-only 基线。
8. 一个不使用 reranker 的 dense retrieval 基线。

为了区分召回和重排贡献，另加交叉组合：用同一组固定候选分别送入 Qwen3 Reranker 0.6B / 4B / 8B 与 BGE Reranker。不要只测“Qwen 对 Qwen、BGE 对 BGE”的配对组合。

## 4. 公开 benchmark：用什么与业界对标

### 4.1 基准选用矩阵

| Benchmark | 主要用途 | 要读取的核心指标 | 在项目里的定位 |
|---|---|---|---|
| [MTEB](https://leaderboard.mteb.org/) | 通用文本向量任务；含检索、分类、聚类、STS、重排等 | 必须单列 Retrieval、Reranking；不要只看 Mean(Task) | 通用能力主参考，适合横向筛选 Embedding |
| [MTEB English v2](https://leaderboard.mteb.org/benchmark/MTEB%28eng%2C%20v2%29) | 英文任务，强调较真实的泛化和较少常见训练集的任务 | Retrieval 主要看 nDCG@10 等任务主指标 | 英文手册和英文技术资料对标 |
| [C-MTEB / MTEB Chinese](https://github.com/FlagOpen/FlagEmbedding/tree/master/research/C_MTEB) | 中文嵌入任务；经典版本含 31 个测试数据集 | Retrieval、Reranking、STS，以及 Mean(Task) | 中文能力主参考；要锁定具体版本 |
| [MMTEB](https://arxiv.org/abs/2502.13595) | 多语言扩展，覆盖更多语言和任务 | 看与业务语言相关的任务分数，不只看总平均 | 中文/英文/跨语言能力补充 |
| [BEIR](https://arxiv.org/abs/2104.08663) | 多领域、零样本信息检索泛化评估；原始论文选取 18 个公开数据集 | 通常重点看各数据集 nDCG@10，并报告平均值与方差 | 检查模型在训练分布外的泛化，特别是陌生技术领域 |
| [MLDR / MultiLongDocRetrieval](https://github.com/FlagOpen/FlagEmbedding) | 长文档检索，多语言设置 | nDCG@10、Recall@K，按其官方实现报告 | 长手册、技术标准、工艺规范的重点补充 |
| [MIRACL](https://github.com/project-miracl/miracl) | 多语言检索 | nDCG@10 等检索指标 | 多语言与跨语言补充；按实际语言选任务 |
| [FollowIR](https://huggingface.co/datasets) / Qwen 官方 reranker 对标表 | 检查是否遵循查询里的具体检索约束 | 采用 benchmark 官方定义的指标 | 验证“必须满足某个条件”的检索指令遵循能力 |
| 内部半导体检索集 | 企业真实语料、术语、权限与版本 | Recall@K、nDCG@K、MRR、延迟、失败率 | **最终验收主依据**，不能由公开榜单替代 |

MTEB 文档支持本地运行和自建 benchmark；MTEB 榜单按任务、模型大小、模型架构、语言等维度查看。参见 [MTEB 文档与 leaderboard 说明](https://docs.mteb.org/get_started/usage/leaderboard/)、[MTEB 任务列表](https://leaderboard.mteb.org/tasks)。

### 4.2 不要错误使用平均分

- **Mean(Task)**：多个任务主指标平均值，衡量广义能力，但可能掩盖检索任务表现。
- **Mean(Type)**：任务类型聚合平均，便于观察检索、聚类、分类等类别，不等价于真实知识库收益。
- **Retrieval**：应优先用于 Embedding 检索能力对比。
- **Reranking**：应优先用于 Embedding 或 Reranker 的相关性排序任务，但需要核对榜单具体测试定义。
- **内部 RAG**：生成答案的正确率不仅受向量与重排影响，还受分块、生成模型、提示词、上下文长度影响，必须单独评估。

**建议公开 benchmark 最少交付**：MTEB 中文相关检索任务、MTEB English v2 Retrieval、MMTEB 中业务相关语言、BEIR 子集、MLDR；资源不足时可先选固定子集，但必须在结果中声明任务清单，不能拿未完整运行的子集宣称复现了整个榜单。

## 5. 官方公布结果：作为参考线，而非内网保证值

### 5.1 Qwen3-Embedding 官方模型卡数值

Qwen 官方模型卡发布的静态对比表中，以下为其所列指标。模型卡对 MTEB multilingual 对比注明其对比数据取自 **2025-05-24** 的在线 MTEB 榜单；English v2 / C-MTEB 表也应当视为模型卡公布时的参考快照，不等于 2026-10-21 动态排行榜的实时第一名。

**MTEB Multilingual 官方表摘录：**

| 模型 | 参数量 | Mean(Task) | Retrieval | Rerank |
|---|---:|---:|---:|---:|
| BGE-M3 | 0.6B | 59.56 | 54.60 | 62.79 |
| multilingual-e5-large-instruct | 0.6B | 63.22 | 57.12 | 62.61 |
| Qwen3-Embedding-0.6B | 0.6B | 64.33 | 64.64 | 61.41 |
| Qwen3-Embedding-4B | 4B | 69.45 | 69.60 | 65.08 |
| Qwen3-Embedding-8B | 8B | 70.58 | 70.88 | 65.63 |

来源：[Qwen3-Embedding-8B 官方模型卡 Evaluation 表](https://huggingface.co/Qwen/Qwen3-Embedding-8B)。这里的 Retrieval / Rerank 是模型卡特定 benchmark 套件中的聚合列，不应误读成“企业知识库的 Recall@10”。

**MTEB English v2 官方表摘录：**

| 模型 | Mean(Task) | Retrieval | Rerank |
|---|---:|---:|---:|
| Qwen3-Embedding-0.6B | 70.70 | 61.83 | 48.18 |
| Qwen3-Embedding-4B | 74.60 | 68.46 | 50.76 |
| Qwen3-Embedding-8B | 75.22 | 69.44 | 51.56 |

**C-MTEB 官方表摘录：**

| 模型 | Mean(Task) | Retrieval | Rerank |
|---|---:|---:|---:|
| Qwen3-Embedding-0.6B | 66.33 | 71.03 | 62.58 |
| Qwen3-Embedding-4B | 72.27 | 77.03 | 66.05 |
| Qwen3-Embedding-8B | 73.84 | 78.21 | 66.99 |

**官方表能支持的结论**：在模型卡公布的这几个聚合指标里，8B 整体高于同系列 4B / 0.6B；但增益不是每个子任务都相同。Embedding 8B 的中文 Retrieval 比 0.6B 高 7.18 分（78.21−71.03），这是公开参考数据里的聚合分数差，不代表内部检索 Recall 也会提升相同比例。

### 5.2 Qwen3-Reranker 官方表

Qwen3-Reranker 模型卡公开如下对比结果：

| 模型 | 参数量 | MTEB-R | CMTEB-R | MMTEB-R | MLDR | MTEB-Code | FollowIR |
|---|---:|---:|---:|---:|---:|---:|---:|
| Qwen3-Reranker-0.6B | 0.6B | 65.80 | 71.31 | 66.36 | 67.28 | 73.42 | 5.41 |
| Qwen3-Reranker-4B | 4B | 69.76 | 75.94 | 72.74 | 69.97 | 81.20 | 14.84 |
| Qwen3-Reranker-8B | 8B | 69.02 | 77.45 | 72.94 | 70.19 | 81.22 | 8.05 |
| BGE-reranker-v2-m3 | 0.6B | 57.03 | 72.16 | 58.36 | 59.51 | 41.38 | -0.01 |

**解读：**

- 8B 在表中 CMTEB-R、MMTEB-R、MLDR 上略高于 4B；MTEB-R 与 FollowIR 则是 4B 更高。
- Code 指标中 4B / 8B 接近；0.6B 仍可作为低成本强基线。
- 表格注明这些结果使用**Qwen3-Embedding-0.6B 召回的 top-100 候选**进行重排。因此其结论是特定候选集、特定数据和官方实现下的重排结果，不能直接等价为“换上 8B 后生产链路必然提高相同分数”。
- 此表也说明：**“最大参数量必然最佳”是错误选型假设**。最终需要比较 4B 与 8B 的质量增益和延迟/成本增量。

来源：[Qwen3-Reranker-8B 官方模型卡 Evaluation](https://huggingface.co/Qwen/Qwen3-Reranker-8B)。具体版本更新后，请在报告中存档模型卡、下载 revision 和 benchmark 日期。

## 6. 统一测试集设计：公开集 + 半导体内部集

### 6.1 内部数据规模建议

先建立可手工审查的高质量测试集，之后再扩容。推荐规模：

| 阶段 | Query 数量 | 每个 Query 建议标注量 | 用途 |
|---|---:|---|---|
| Smoke / 冒烟 | 30–50 | 至少 1 个正例、若干难负例 | 确认脚本、模型接口、索引能正确运行 |
| Pilot / 试点 | 200–300 | 1–5 个相关文档，包含相关等级 | 比较候选模型，发现数据与标注问题 |
| 正式验收 | 800–2,000 起 | 相关文档池尽可能完整；支持 0/1/2/3 相关等级 | 决策、发布门槛与回归测试 |
| 持续回归 | 每次新增 50–100 个经审核案例 | 覆盖最近的故障、术语、文档和误召回 | 跟踪模型、索引和文档变化 |

以上为项目规划建议，不是外部 benchmark 的固定标准。样本量足够与否应结合问题类型、置信区间和标注一致性判断。

### 6.2 Query 类别分层

正式测试集建议按以下标签分层，统计每类数据单独分数，防止总分掩盖关键缺陷：

1. **直接事实查询**：某设备模块的规格、工艺流程定义、材料说明。
2. **同义表达 / 口语表达**：工程师日常问法与文档正式写法不一致。
3. **缩写 / 别名 / 中英术语**：例如设备简称、工艺缩写、不同命名体系。
4. **精确标识符**：报警码、设备编号、配方号、零件料号、文档编号。
5. **数值约束**：要求匹配值、区间、单位、条件；数值错误的相近结果作为 hard negative。
6. **复杂条件组合**：设备型号 + 工艺步骤 + 特定材料/参数的联合约束。
7. **跨语言检索**：中文 Query 对英文文档、英文 Query 对中文文档。
8. **长文档定位**：正确内容在长手册较后位置或长章节中。
9. **表格 / 列表 / 结构化条目**：需要结合列名、行名或上级标题解释。
10. **相似但不适用的难负例**：相邻型号、近似报警码、旧 recipe、相同术语的不同工艺条件。
11. **版本与时效**：当前有效规范与过期文档；需把正确版本放在前面。
12. **无答案 / 不可回答**：语料中不存在可靠依据，检查系统是否错误召回“看上去相似”的段落。
13. **权限场景**：用户无权访问的文档不得返回；该项是检索系统安全验收，不能只靠模型打分验证。

### 6.3 半导体领域重点场景

- 制程工艺：工艺步骤、窗口条件、参数上下限、前后步骤依赖。
- 设备：设备系列、腔体/模块、部件、保养、校准、故障现象。
- 良率分析：缺陷分类、异常现象、根因描述、处理措施、相似案例。
- 规格与材料：化学品、耗材、零件、材料兼容性与版本差异。
- 故障代码：报警码 exact match、同码不同设备语境、近似代码 hard negative。
- 技术报告：跨页表格、附录、图表标题、报告结论与原始数据的区分。
- 知识图谱关联：实体别名、设备—部件—报警—处理措施之间的关系；向量模型只负责语义召回，关系路径准确性需另建图查询评测。

### 6.4 标注标准

- 至少两位领域人员复核高风险案例；随机抽检不少于 10% 的标签。
- 推荐使用分级相关性：`3=直接回答问题/正确约束均满足`，`2=高度相关且可支持回答`，`1=部分相关/背景信息`，`0=不相关或条件冲突`。
- 对精确参数、版本和报警代码等高风险任务，采用更严格规则：关键约束错误的候选即使语义相似，也应标为 0 或根据规则判为不适用。
- 不能只从当前模型的 Top-K 里找正例；应合并 BM25、多个 Embedding、人工检索和业务专家提供的已知答案，构建更完整的相关文档池。
- 划分 train/dev/test 时，以文档来源、文档家族或时间切分，避免同一文档相邻段落同时出现在开发集与测试集，导致“记住模板”的假高分。
- 测试集文件不得被用于微调；需要保留一份受控的隐藏验收集。

## 7. 指标体系与计算口径

### 7.1 Embedding 初召回指标

设每个 query 的相关文档集合为 `Rel(q)`，系统返回的前 K 个文档为 `TopK(q)`。

| 指标 | 定义/用途 | 推荐 K 值 | 解释注意事项 |
|---|---|---|---|
| Hit Rate@K / Success@K | `TopK` 中是否至少有一个相关文档，之后对 Query 取平均 | 1、5、10、20 | 只衡量“是否至少命中”，不体现排序和完整召回 |
| Recall@K | `|TopK ∩ Rel| / |Rel|`，对 Query 平均 | 5、10、20、50、100 | 重点反映初召回是否把证据找齐；相关集不完整会扭曲结果 |
| Precision@K | `|TopK ∩ Rel| / K` | 5、10、20 | K 个结果中有多少是相关结果；对 RAG 上下文噪声有参考价值 |
| MRR@K | 第一个相关结果排名倒数的平均值；K 之后没有相关命中记 0 | 5、10、20 | 适合“第一条结果是否正确”的检索使用体验 |
| nDCG@K | 对分级相关性按排名折损，并按理想排序归一化 | 5、10、20 | 最推荐的综合排序指标；需要明确相关等级和 gain 函数 |
| MAP@K | 对相关结果的平均精确率取平均 | 10、20、100 | 更看重多个相关结果的排序；相关集合需要较完整 |
| Coverage | 至少命中一个相关结果的 Query 比例 | 10、20 | 适合定位全无命中的问题类型 |
| Empty / Abstain Accuracy | 无答案 Query 被正确判定“无可靠结果”的比例 | 固定阈值策略 | 纯向量相似度排名本身不等于可信的拒答能力 |

**生产建议主指标**：初召回以 `Recall@20` / `Recall@50` 为主，辅助 `nDCG@10`、`MRR@10` 和 `Hit@5`。若 Reranker 只处理 top-20，初召回的 `Recall@20` 是关键门槛；如果候选池只包含 top-10 以外也需要引用的结果，则同时报告更大的 K。

### 7.2 Reranker 排序指标

Reranker 的评测必须在固定候选集上进行。每个 Query 的候选文档及其标注在各模型间保持相同。

| 指标 | 说明 | 推荐用途 |
|---|---|---|
| nDCG@5 / nDCG@10 | 适合分级相关性，衡量相关结果是否前置 | 最主要重排指标 |
| MRR@5 / MRR@10 | 第一个相关结果是否被排到前面 | 用户通常只看少量结果时很有价值 |
| Precision@5 / @10 | 重排后前几条的准确程度 | 衡量 RAG 上下文污染风险 |
| MAP@10 / MAP@100 | 多个相关结果的排序质量 | 需要多证据任务 |
| Pairwise Accuracy | 标注偏好对中，模型是否把优选文档排在较差文档前 | 对难负例与成对标注适用 |
| Top-1 Accuracy | 第一名是否满足直接回答/严格约束 | 报警码、配方号、标准条款等任务 |
| ΔnDCG@10 | `重排后 nDCG@10 - 重排前 nDCG@10` | 衡量 Reranker 的净提升 |
| ΔMRR@10 | 重排前后 MRR 的差值 | 衡量首个相关结果是否改善 |

**关键约束**：同时记录重排前和重排后成绩。只报重排后的高分，会无法判断收益是来自好的初召回还是好的 Reranker。

### 7.3 系统与性能指标

| 指标 | 定义 | 测法 |
|---|---|---|
| Query latency P50/P95/P99 | 单条请求时延分位数 | 预热后固定 QPS、多轮重复，包含/不包含网络时间分别记录 |
| Throughput | queries/s 或 document-pairs/s | 固定 batch、长度分布和并发级别；Embedding 与 Reranker 分别报告 |
| Encoding throughput | tokens/s、docs/s | 按平均输入 token、长度分桶报告 |
| GPU memory peak | 峰值显存 | 记录空载、加载、批量推理及压力测试峰值 |
| CPU/RAM | CPU 占用、进程 RSS、系统 RAM 峰值 | 持续压力测试而非仅截图单次推理 |
| Startup time | 服务启动到健康检查通过 | 冷启动与模型缓存命中分别测 |
| Error rate | 超时、OOM、服务错误占比 | 与性能测试一起记录 |
| Cost per 1M queries / documents | GPU 小时或机器成本换算 | 统一内部成本口径；报告参数、batch、平均 token |
| Index footprint | 向量库容量、每百万分块占用 | 记录向量维度、dtype、元数据和索引结构 |
| Robustness | 不同长度、语言、噪声、难负例下的分数变化 | 按测试标签分桶并计算相对下降 |

### 7.4 Embedding 特有控制变量

- **向量维度**：Qwen3 Embedding 支持 MRL，不能只测默认最大维度。至少测试最大维度与一个较小维度（例如 1024；前提是所选模型支持），记录精度与索引体积/延迟的变化。
- **归一化**：确认 query 与 corpus 向量都采用一致的归一化规则。归一化向量的点积等价于 cosine similarity；不归一化时点积不可直接当成 cosine。
- **距离函数**：cosine、inner product、L2 必须与向量预处理匹配。不能用 A 模型用 cosine、B 模型用错误的 L2 作为比较。
- **Query 指令**：至少对 Qwen3 测 `默认/官方 query 指令` 与 `业务定制指令`。Document 侧是否加指令也必须保持在文档明确规定的方式。
- **输入长度**：短文本、典型 chunk、长段落分别统计；不要因为官方上限很长就把所有文档塞进单个长输入。
- **截断策略**：记录 `max_length`、截断方向和平均/最大 token 数。

### 7.5 Reranker 特有控制变量

- 固定 candidate pool：主实验推荐由一个确定的召回基线得到 top-100，另做 top-20 / top-50 / top-200 的候选数量敏感性分析。
- 固定候选来源与排序：输入完全相同，原候选的初始排名单独存档。
- 固定 prompt / instruction：先复现模型默认模板，再评估半导体业务定制模板；不能一个模型用业务提示、另一个模型用默认提示后直接比较。
- 固定最大 token 长度与截断方式，尤其是 query + document + instruction 拼接后的总 token。
- 对打分进行**排序评估**即可，不要比较不同模型原始 logit 的绝对大小。Qwen reranker 官方示例说明默认可输出 raw logit 差值，score 标度不一定具备跨模型可比性。
- 记录 batch size、精度（BF16/FP16/量化）、并发、padding 策略及 OOM/超时。

## 8. 建议的综合评分与验收规则

### 8.1 推荐权重

这是本项目建议权重，不是 MTEB 或业界强制标准。应根据知识库使用方式调整，但测试开始后不允许为了让某一模型获胜而临时改权重。

| 一级维度 | 权重 | 二级指标建议 |
|---|---:|---|
| 检索质量 | 35% | 内部 Recall@20、nDCG@10、MRR@10；公开 C-MTEB / MTEB Retrieval 作补充 |
| 重排收益 | 25% | 内部 nDCG@10、MRR@10、Precision@5、ΔnDCG@10 |
| 半导体专项能力 | 15% | exact match、数值/单位约束、版本区分、难负例、跨语言分层分数 |
| 推理性能 | 10% | P95 延迟、吞吐、启动时间、错误率 |
| 资源与成本 | 10% | 峰值显存、GPU 小时、索引空间、每百万查询成本 |
| 稳健与可运维性 | 5% | 长度敏感性、重复性、模型可离线部署、版本可追踪 |

建议每项指标先映射到 0–100 的子分，再按固定权重汇总。不要把原始 nDCG（0–1）、延迟（毫秒）和显存（GB）直接相加。

### 8.2 硬门槛优先于加权总分

可先把以下值作为**试点阶段的建议验收线**，然后根据第一轮结果、标注质量和业务风险修订一次，形成冻结版本：

- 内部 `Recall@20` ≥ 0.90（对标注完整的可回答 Query 子集）。
- 内部 `nDCG@10` ≥ 0.75（采用分级相关性；阈值需要通过 pilot 校准）。
- 对报警码 / 型号 / 版本等严格约束 Query，`Top-1` 正确率 ≥ 0.95；高风险任务若未达标，不允许仅凭整体分数上线。
- 重排后 `nDCG@10` 至少不低于重排前；推荐要求有统计上稳定的正向增益。
- 在目标硬件和约定并发下，P95 延迟、峰值显存、错误率满足服务预算。
- 权限隔离测试必须 100% 通过：无权限文档不得出现在结果、引用或日志返回内容中。

以上数值是**项目建议起点**，不能对外声称是行业统一标准。尤其 nDCG / Recall 的可达值高度依赖语料、Query 难度、标注完整性和 chunk 方式。

### 8.3 统计与可信度

- 所有模型在相同 Query 集上成对比较。
- 对核心指标给出平均值、每类分层值、样本量及 bootstrap 置信区间；如资源允许，做 query-level paired bootstrap。
- 同时报告相对变化和绝对变化，例如 `nDCG@10 +0.035` 与 `相对提升 4.8%`，不要只报百分比。
- 对模型差异较小的情况，不应凭 1 次运行作结论。至少重复性能测试 3 轮；指标计算脚本应确定性可复跑。
- 公开榜单只能作为先验依据，最终排序以固定内测集、固定硬件和明确成本预算为准。

### 10.2 `eval_embedding.py`

用途：加载一个 Sentence Transformers 兼容的 Embedding 模型，对本地 `corpus.jsonl` 和 `queries.jsonl` 编码，计算 Recall@K、Hit@K、MRR@K、nDCG@K；输出逐 Query 命中信息和汇总 JSON。

```python
#!/usr/bin/env python3
"""Local embedding retrieval evaluation for JSONL corpus and queries.

Expected corpus.jsonl rows: {"id": str, "text": str, ...}
Expected queries.jsonl rows:
  {"id": str, "text": str, "relevant_doc_ids": [str, ...], ...}

This is a compact internal evaluator, not a substitute for official MTEB runs.
"""
from __future__ import annotations

import argparse
import json
import time
from pathlib import Path
from typing import Any

import numpy as np
from sentence_transformers import SentenceTransformer


def read_jsonl(path: str) -> list[dict[str, Any]]:
    rows: list[dict[str, Any]] = []
    with open(path, "r", encoding="utf-8") as f:
        for line_no, line in enumerate(f, 1):
            line = line.strip()
            if not line:
                continue
            try:
                row = json.loads(line)
            except json.JSONDecodeError as exc:
                raise ValueError(f"{path}:{line_no}: invalid JSON: {exc}") from exc
            rows.append(row)
    if not rows:
        raise ValueError(f"No records found in {path}")
    return rows


def dcg(relevances: list[int]) -> float:
    return sum((2.0 ** rel - 1.0) / np.log2(i + 2.0)
               for i, rel in enumerate(relevances))


def metrics_for_query(ranked_ids: list[str], relevant_ids: set[str], k: int) -> dict[str, float]:
    top = ranked_ids[:k]
    hits = [1 if doc_id in relevant_ids else 0 for doc_id in top]
    hit_rate = float(any(hits))
    recall = len(set(top) & relevant_ids) / max(1, len(relevant_ids))
    precision = sum(hits) / max(1, k)
    reciprocal_rank = 0.0
    for rank, hit in enumerate(hits, 1):
        if hit:
            reciprocal_rank = 1.0 / rank
            break
    # Binary relevance is used by this compact script. Use graded qrels for official-style nDCG.
    gains = [1 if hit else 0 for hit in hits]
    ideal = sorted(gains, reverse=True)
    idcg = dcg(ideal)
    ndcg = dcg(gains) / idcg if idcg > 0 else 0.0
    return {
        "hit_rate": hit_rate,
        "recall": recall,
        "precision": precision,
        "mrr": reciprocal_rank,
        "ndcg": ndcg,
    }


def main() -> None:
    parser = argparse.ArgumentParser()
    parser.add_argument("--model", required=True, help="HF model ID or local model directory")
    parser.add_argument("--corpus", default="data/corpus.jsonl")
    parser.add_argument("--queries", default="data/queries.jsonl")
    parser.add_argument("--output", default="results/embedding_eval.json")
    parser.add_argument("--ks", default="5,10,20,50")
    parser.add_argument("--batch-size", type=int, default=32)
    parser.add_argument("--device", default=None, help="cuda, cpu, etc.; default is library selection")
    parser.add_argument("--normalize", action="store_true", help="L2-normalize vectors for cosine/IP ranking")
    parser.add_argument("--query-prefix", default="", help="Optional fixed query instruction/prefix")
    args = parser.parse_args()

    corpus = read_jsonl(args.corpus)
    queries = read_jsonl(args.queries)
    if any("id" not in x or "text" not in x for x in corpus):
        raise ValueError("Every corpus row must contain id and text")
    if any("id" not in x or "text" not in x or "relevant_doc_ids" not in x for x in queries):
        raise ValueError("Every query row must contain id, text, relevant_doc_ids")

    doc_ids = [str(x["id"]) for x in corpus]
    doc_texts = [str(x["text"]) for x in corpus]
    query_ids = [str(x["id"]) for x in queries]
    query_texts = [args.query_prefix + str(x["text"]) for x in queries]
    relevant = {str(x["id"]): {str(d) for d in x["relevant_doc_ids"]} for x in queries}

    model_kwargs = {} if args.device is None else {"device": args.device}
    model = SentenceTransformer(args.model, **model_kwargs)

    t0 = time.perf_counter()
    doc_vecs = model.encode(doc_texts, batch_size=args.batch_size,
                            normalize_embeddings=args.normalize,
                            convert_to_numpy=True, show_progress_bar=True)
    doc_seconds = time.perf_counter() - t0
    t1 = time.perf_counter()
    query_vecs = model.encode(query_texts, batch_size=args.batch_size,
                              normalize_embeddings=args.normalize,
                              convert_to_numpy=True, show_progress_bar=True)
    query_seconds = time.perf_counter() - t1

    # For normalized vectors this is cosine similarity. Otherwise this is dot product.
    scores = np.asarray(query_vecs) @ np.asarray(doc_vecs).T
    ks = sorted(set(int(x) for x in args.ks.split(",") if x.strip()))
    if not ks or any(k <= 0 for k in ks):
        raise ValueError("--ks must contain positive integers, e.g. 5,10,20")

    per_query: list[dict[str, Any]] = []
    summary: dict[str, Any] = {
        "model": args.model,
        "corpus_size": len(corpus),
        "query_count": len(queries),
        "embedding_dimension": int(doc_vecs.shape[1]),
        "normalized": args.normalize,
        "query_prefix": args.query_prefix,
        "doc_encode_seconds": round(doc_seconds, 4),
        "query_encode_seconds": round(query_seconds, 4),
        "metrics": {},
    }

    order = np.argsort(-scores, axis=1)
    for i, q in enumerate(queries):
        ranked = [doc_ids[j] for j in order[i]]
        row: dict[str, Any] = {
            "query_id": query_ids[i],
            "relevant_doc_ids": sorted(relevant[query_ids[i]]),
            "top_results": [
                {"doc_id": doc_ids[j], "score": float(scores[i, j]), "rank": rank + 1}
                for rank, j in enumerate(order[i, : max(ks)])
            ],
            "metrics": {},
        }
        for k in ks:
            m = metrics_for_query(ranked, relevant[query_ids[i]], k)
            row["metrics"][str(k)] = m
        per_query.append(row)

    for k in ks:
        q_metrics = [row["metrics"][str(k)] for row in per_query]
        summary["metrics"][str(k)] = {
            name: round(float(np.mean([m[name] for m in q_metrics])), 6)
            for name in ("hit_rate", "recall", "precision", "mrr", "ndcg")
        }

    result = {"summary": summary, "per_query": per_query}
    out = Path(args.output)
    out.parent.mkdir(parents=True, exist_ok=True)
    out.write_text(json.dumps(result, ensure_ascii=False, indent=2), encoding="utf-8")
    print(json.dumps(summary, ensure_ascii=False, indent=2))
    print(f"Detailed results saved to: {out.resolve()}")


if __name__ == "__main__":
    main()
```

> **注**：上述代码中的指标实现是二值相关性版本，适合快速比较。正式 nDCG / MAP 应使用分级 qrels，并经代码审查；若采用当前脚本，请将其作为 smoke/pilot 用的轻量工具。对 Qwen3-Embedding 的正式复现，应使用官方建议的 query instruction 模板并记录其内容。

### 10.3 Reranker 最小测试逻辑

Reranker 的核心测试流程应是：

1. 从冻结的候选集文件中读取每个 Query 与候选文档。
2. 使用同一模型版本、同一 instruction、同一 max length 为每个 query-document pair 打分。
3. 按模型分数重新排序；计算排序前后 nDCG@10、MRR@10、Precision@5、Top-1 Accuracy。
4. 对候选集 top-20、top-50、top-100 分别做实验；保留 rerank 前的原始排名。
5. 记录每一批的输入 token、推理耗时、显存、异常与完整模型参数。

Qwen 官方示例可参考 [Qwen3-Reranker-8B 模型卡](https://huggingface.co/Qwen/Qwen3-Reranker-8B) 中的 Transformers / Sentence Transformers 用法。示例接口的关键点：将每个查询与候选段落组成 pair，使用同一任务说明；该模型分数用于排序，不要把其原始分数当作跨模型校准后的概率。

### 10.4 Smoke tests（功能测试用例）

| ID | 测试场景 | 输入构造 | 通过条件 |
|---|---|---|---|
| SM-01 | 完全匹配 | Query 与正例包含同一唯一标识符 | 正例进入预期 Top-K |
| SM-02 | 语义改写 | Query 不复用文档原词，但语义一致 | 同义正例优先于不相关项 |
| SM-03 | Hard negative | 同型号不同版本/参数作为负例 | 满足全部约束的文档排名更高 |
| SM-04 | 中文问英文文档 | 中文 Query，英文答案段落 | 跨语言正例被召回 |
| SM-05 | 长文本尾部命中 | 关键答案位于长文档末尾 | 按定义的 max_length / chunk 方案能召回 |
| SM-06 | 空答案 | Corpus 内无答案，保留近似干扰项 | 评测器正确记录为无正例；拒答另由系统阈值判断 |
| SM-07 | 重排提升 | 固定候选里把正例初始排到后面 | reranker 应提升，或记录该例为失败样本供分析 |
| SM-08 | 错误输入 | 缺字段、重复 ID、坏 JSONL | 明确报错，不静默地产生分数 |
| SM-09 | 可重复性 | 相同模型、输入、参数运行两次 | 排名一致；分数差在约定容差内 |
| SM-10 | 权限隔离 | 正例文档在用户不可访问集合中 | 任何 API / UI / MCP 返回都不得曝光该文档 |

这些测试通过只是说明评测流程基本正确，不意味着模型达到业务验收标准。

## 11. 官方 Benchmark 复现流程

### 11.1 复现准则

每一轮公开 benchmark 复现，必须保存：

- 评测框架版本（例如 `mteb` 的精确版本 / Git commit）。
- 数据集名称、版本、split、revision 或下载快照。
- 模型 repo ID、具体 revision/commit、权重精度与文件 hash。
- 自定义 query 指令、文档格式、max length、输出维度、归一化设置。
- batch size、设备、GPU 型号、CUDA、驱动、PyTorch / Transformers 版本。
- 运行命令、开始结束时间、日志、原始 per-task scores。
- 与公开榜单不同的任何设置及原因。

### 11.2 MTEB 运行建议

遵循当前 [MTEB 官方文档](https://docs.mteb.org/) 获取安装与任务执行方法。不要长期复制其他博客的旧 CLI 命令：MTEB 版本和任务 API 会变化。建议固定一版依赖、显式选取任务、先跑一个小任务冒烟，再启动整批评测。结果至少保留 per-task 分数，并将总体分数与官方 leaderboard 同名任务逐项核对。

示意命令（**以安装版本的官方文档为准，任务名需要通过当前 MTEB API 核实**）：

```bash
pip install "mteb==<经过验证的固定版本>"
python - <<'PY'
import mteb
print("installed mteb version:", getattr(mteb, "__version__", "unknown"))
# 使用当前版本的 mteb.get_task(...) / MTEB(...).run(...) API；
# 具体任务构造和模型 adapter 按 docs.mteb.org 的当前示例固定。
PY
```

MTEB 官方文档说明，可在本地运行评测，也支持自建任务 / benchmark；这适合把内部半导体测试集整理成固定 task，但需要给出清晰的数据格式、相关标签与 scoring function。

### 11.3 BEIR / MLDR / C-MTEB

- **BEIR**：按官方仓库的数据加载、检索器和评测协议运行。优先关注不同领域的 nDCG@10；汇总时同时展示逐数据集成绩，不能只留一个均值。
- **C-MTEB**：锁定项目代码和数据版本，优先运行与检索有关的任务；如果报告整体分数，要注明任务数量与是否完整执行。
- **MLDR**：按官方 FlagEmbedding / MLDR 流程，明确语言、query / passage max length、chunk 处理、模型指令及指标。该类任务对长文本处理细节较敏感，不能只对照论文中某一数值而不对齐配置。
- **MMTEB**：因任务和语言覆盖较广，第一轮按企业实际语言选子集，再在报告中注明它是“业务相关子集”，不要标记为完整复现。

## 12. 内网部署与性能测试建议

### 12.1 部署路径建议

| 路径 | 适用 | 优点 | 注意事项 |
|---|---|---|---|
| Transformers / Sentence Transformers | 最便于做单机对照评测、理解模型输入与输出 | 接口灵活，适合快速验证 | 高并发服务能力需另行调优；版本兼容要锁定 |
| vLLM Embedding | Qwen3 Embedding 的批量 / 服务化候选路径；官方模型卡给出 `vllm` 示例 | 连续批处理和服务化能力，便于压测 | 使用当前支持该任务类型的版本；需实测输出是否与官方评测方式一致 |
| Text Embeddings Inference（TEI） | Embedding 服务 | HTTP 服务接口、容器化 | 部署前确认当前镜像版本支持目标模型架构和硬件；官方示例版本不代表 2026 年最新版本 |
| FlagEmbedding | BGE-M3、BGE reranker、混合检索及官方评测参考 | 与 BGE 生态和官方示例对齐方便 | 锁定版本，并区分 dense/sparse/multi-vector 工作模式 |
| Transformers / CrossEncoder | Qwen3 Reranker 单机实验及可控性测试 | 易于复现模型卡用法 | 8B 重排需要控制候选批量和输入 token，不能直接按小模型吞吐假设部署 |

### 12.2 显存与硬件估算原则

粗略权重显存可先按参数量乘以每参数字节估算：BF16 / FP16 权重大约 2 bytes/parameter，因此 8B 模型的权重理论量级约 16 GB；实际部署还要额外考虑 CUDA context、激活、中间张量、batch、输入长度和服务框架开销。该值只用于初筛硬件，不是可运行性保证。

- 单个 8B 模型：优先用 24 GB 及以上显存设备做小 batch 验证；如果序列较长、batch 较大或要稳定承载并发，优先考虑 48 GB 级别或多卡方案。
- Embedding 8B 与 Reranker 8B 同时常驻：不要假设一张 24 GB 卡足够；先分别部署/压测，再决定同卡、分卡、量化或动态加载。
- 比较模型时必须报告显卡型号、显存、精度和 batch；不同硬件下“快几倍”的结论不具可迁移性。
- Embedding 编码大语料时，区分模型推理吞吐和向量索引构建吞吐；后者还受 CPU、磁盘、索引参数影响。
- 长上下文上限是模型能力参数，不代表建议单次输入到最大长度。对 RAG，分块策略需要与模型一起评估。

### 12.3 建议上线前性能矩阵

每个候选模型在以下组合下分别测试：

- 输入长度：短（P50）、常规（P90）、长（P99 / 长文档子集）。
- Batch：1、4、8、16（根据显存上限调整）。
- 并发：1、2、4、8、16（以实际接口承载能力为准）。
- 预热：无缓存冷启动、热缓存、稳定运行至少 30 分钟。
- 请求类型：纯 Embedding、纯 reranking、完整检索链路。
- 结果：P50/P95/P99 latency、QPS、tokens/s、峰值显存、CPU/RAM、失败率、输出数量和结果一致性。

压测需要先设置合理的 timeout 和熔断行为；避免把 OOM 后自动重试的重复工作误算为成功吞吐量。

### 12.4 离线导入内网流程

1. 在可联网环境确认模型许可、模型 revision 与依赖版本。
2. 下载模型、tokenizer、配置和所需数据集到暂存区；记录 SHA256、来源 URL、下载日期、许可及版本。
3. 下载 Python wheel / Conda 包 / 容器镜像及其依赖，生成离线安装清单；注意 GPU 驱动与 PyTorch CUDA wheel 的兼容性。
4. 对测试数据脱敏并检查是否含公司机密；仅将获得许可的公开 benchmark 数据带入内网。
5. 内网断网运行一次 `local_files_only=True`（或框架对应的离线参数）验证，关闭不必要的模型遥测与外网请求。
6. 记录运行环境、模型 hash 和评测报告。每次模型或依赖升级都要跑 smoke tests 和核心回归集。

### 12.5 Hugging Face 缓存与完全离线

建议以模型本地目录路径加载模型，并在隔离环境中关闭 Hub 在线查找。以 Transformers 为例，可设置：

```bash
export HF_HUB_OFFLINE=1
export TRANSFORMERS_OFFLINE=1
```

不同库对离线模式支持程度不同，应以所用版本文档为准。必须验证 tokenizer、config、model shards、特殊 token 与必要依赖都存在；仅复制权重文件通常不足以正常加载。

## 14. 推荐实施顺序

### Phase 0：冻结评测协议

- 确定候选模型清单、版本和许可。
- 准备 30–50 条 smoke case，检查数据与代码。
- 确认指标定义、评测硬件、batch、max length、指令和向量距离函数。
- 确定内部测试集维护人与标注规则。

### Phase 1：公开 benchmark 基线

- 复现 Qwen3 / BGE 公开资料中的主要检索基准；先运行相关的 retrieval 任务，再逐步扩展。
- 输出逐任务分数，而不只是一个总分。
- 将官方参考值、当前榜单值、本地复现值放在不同列。

### Phase 2：内部初召回对比

- 用相同 corpus、相同 chunk 和固定 query 集比较所有 Embedding。
- 先用精确相似度搜索隔离模型本身差异；再用生产向量数据库评估 ANN 索引的近似误差。
- 比较默认维度、缩小维度、instruction、有无 instruction、不同 chunk 长度。

### Phase 3：固定候选集的 Reranker 对比

- 由基线初召回一次性生成 top-100 候选；冻结候选内容和顺序。
- 比较 Qwen3-Reranker 0.6B/4B/8B 与 BGE reranker。
- 报告重排前后排序指标、每 Query 变化、困难类别变化与延迟。
- 再增加不同候选来源，以验证 reranker 是否只适合某一特定初召回器。

### Phase 4：端到端系统测试

- 评估 dense-only、BM25-only、hybrid、rerank 后的链路。
- 检查 top-k、融合策略、rerank candidate count、分块长度与向量维度的组合。
- 若评估完整 RAG，再单独测答案正确性、引用支持度、无依据断言和拒答；不要把这些生成层指标直接算作 Embedding 分数。

### Phase 5：部署压测与准入

- 按实际硬件做长度、batch、并发矩阵。
- 进行至少 30 分钟持续压测与重启恢复测试。
- 以硬门槛 + 加权分数决定上线，保留回滚配置和上一版评测结果。

## 15. 当前建议结论

1. **Qwen3-Embedding-8B 与 Qwen3-Reranker-8B 应列为高精度候选，但不能直接预设它们最终胜出。** 8B 是公开基准中的强候选，实际是否采用取决于半导体内部检索收益与部署预算。
2. **一定要测 Qwen3-4B。** Qwen 官方 reranker 表显示，4B 在 MTEB-R 和 FollowIR 上高于 8B；在不少企业环境里，4B 可能有更好的质量/时延比。
3. **Qwen3-0.6B 是不可缺少的成本基线。** 它既适合快速编码和高吞吐，也作为官方 Reranker 对照的一部分。小模型若已满足内部验收线，应认真考虑其运营成本优势。
4. **BGE-M3 的重点是多功能召回而不仅仅是 dense embedding。** 对照时应分别测 dense、sparse lexical 及融合策略；不能用只启用 dense 的单次测试代表 BGE-M3 完整能力。
5. **正式决策以“内部半导体测试集 + 固定候选重排评测 + 目标硬件压测”为主。** 公共榜单用于建立行业参照线，不等于生产场景保证。
6. **最需要防范的评测陷阱**：只看 Mean(Task)、候选集不一致、无指令与有指令混测、Query 与文档截断方式不一致、相关文档池不完整、对重复或泄漏文档过拟合、不同硬件上比较吞吐、用 reranker 原始 logit 跨模型作概率解释。

## 附录 B：最小上线决策规则

只有同时满足以下条件，模型才进入候选上线名单：

- 核心内部检索指标过线，且报警码、数值约束、版本区分、跨语言等关键类别没有严重退化。

- 离线部署成功，模型与依赖版本可追溯，具备故障回滚方案。
